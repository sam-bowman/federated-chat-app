# CLAUDE.md

Guidance for Claude Code (or any coding agent) working in this repository.

## What this is

A federated, open-source communication platform — Discord-style communities and
channels, MSN-style friends/presence/DMs, custom emoticons — with real
server-to-server federation between independently-run homeservers. See
[README.md](README.md) for the full feature list, setup instructions, and
architecture notes; this file is about how to work in the repo, not what it does.

Two npm workspaces:

- `server/` — Node.js + TypeScript, Express, `ws`, Prisma + PostgreSQL
- `client/` — React + TypeScript + Vite

Federation (`server/src/lib/federation/`, `server/src/modules/federation/`) is a
signed HTTP protocol between homeservers — read `docs/federation-architecture.md`
("Architecture notes — federation" and "Known federation limitations") before
changing anything there.

## Commands

Run from the repo root unless noted.

**Dev servers**
- `.\scripts\start.ps1` / `.\scripts\stop.ps1` — single-server local dev (Postgres + server + client). `start.ps1` and `start-federation-demo.ps1` share `scripts\common.ps1`: they only say "up" once `/healthz` answers and the client page loads, fail on a port held by something else, and run `prisma generate` only when the client is missing or older than the schema - **never unconditionally**: on Windows generating over a running server's query engine DLL fails with EPERM.
- `.\scripts\start-federation-demo.ps1` / `.\scripts\stop-federation-demo.ps1` — two independent homeservers (`alice.test` / `bob.test`) for testing federation end to end
- `docker compose up -d redis` — only needed to test multiple replicas of the *same* homeserver (set `REDIS_URL=redis://localhost:6380`); not started by either script above, since a single replica never needs it. See docs/scaling.md "Running multiple replicas".

**Build / typecheck / lint**
- `npm run build --workspace server` — `tsc`
- `npm run build --workspace client` — `tsc -b && vite build`
- `npm run build:binary --workspace client` — builds, then packages `dist/` into a single native executable for the *current* platform (`client/dist-bin/my-chat-client-<platform>-<arch>[.exe]`) via Node's [Single Executable Applications](https://nodejs.org/api/single-executable-applications.html) — see `docs/distribution.md`'s client "Binary" row. Configure it the same way as the Docker image: an `API_URL` env var (unset → picker mode), `PORT`/`HOST` to bind (defaults `8080`/`0.0.0.0`).
- `npm run build:binary --workspace server` — same idea for the server (`server/dist-bin/my-chat-server-<platform>-<arch>[.exe]`, plus a `node_modules/.prisma/client/` folder and `prisma/migrations/` it ships alongside - see `docs/distribution.md`'s server "Native binary" row). Applies pending migrations itself at startup (`server/src/standaloneMigrate.ts`) since it doesn't ship the `prisma` CLI.
- `npm run tauri --workspace client -- dev` / `... -- build` — the desktop app (`client/src-tauri/`, see `docs/distribution.md`'s "Desktop app" row). Note the `--` before `dev`/`build`: without it, npm's own `--workspace` flag swallows the argument instead of passing it through to the `tauri` CLI. `dev` opens a real window pointed at the Vite dev server (inherits whatever `client/.env` sets, same as plain `npm run dev` - expected, not a bug, but means a local dev-mode run can look like fixed-server mode even though a real packaged build won't); `build` produces real installers under `client/src-tauri/target/release/bundle/`.
- `npm run typecheck --workspace server` — also typechecks `server/test/` (the build script above deliberately excludes it, so this is the only thing that checks it)
- `npm run lint --workspace client` — oxlint

**Tests** — see docs/testing.md for the full picture
- `npm run test --workspace server` / `npm run test --workspace client` — unit tests, no database. **Never run a bare `npx vitest run` in `server/` to "run the tests".** The integration tests truncate every table between tests, and without `vitest.integration.config.ts`'s `setupEnv.ts` they connect to whatever `server/.env` says - the real dev database `chat` - and wipe it (this destroyed a dev database once). The default config now runs only `src/**` unit tests, and `test/helpers/db.ts`'s `resetDb()` refuses any database whose name does not end in `_test`; don't weaken either.
- `npm run test:integration --workspace server` — full API + federation tests against a real Postgres database (needs a `chat_test` database — see docs/testing.md). Run it with `REDIS_URL` **unset**: the two Redis-backed test files point themselves at `TEST_REDIS_URL` (defaulting to the dev Redis on `localhost:6380`, so `docker compose up -d redis` is enough; CI passes `TEST_REDIS_URL`, never `REDIS_URL`). Setting `REDIS_URL` globally makes *every* file Redis-backed, including `rateLimit.test.ts`'s deliberately in-memory limiter, whose small limits then collide with counters left in Redis by earlier files - an intermittent `expected 429 to be 401` (vitest reorders files between runs, so it comes and goes), not a real flake.
- `npm run test:e2e` - the real client in a real browser against two real servers (`e2e/`, Playwright; see docs/testing.md "End-to-end tests"). Needs `docker compose up -d postgres` and a browser: `npx playwright install chromium` once, or `E2E_BROWSER_CHANNEL=msedge`. It starts its own servers (:4100/:4101) and clients (:5273/:5274) on databases `chat_e2e_a`/`chat_e2e_b`, which it DROPS and recreates, so it can run beside your demo.
- `npm run test:coverage --workspace <server|client>` / `npm run test:integration:coverage --workspace server` — same, with coverage. The integration run **enforces** a coverage floor (`server/vitest.integration.config.ts`); if a change would drop it, add tests rather than lowering the threshold.

**Database**
- `npx prisma generate --schema server/prisma/schema.prisma` — regenerate the Prisma client after any schema change (do this before `tsc`/editors will see correct types)
- `npx prisma migrate dev` (from `server/`) — create a new migration during development
- A **breaking** schema change that needs a data backfill can't run non-interactively via `prisma migrate dev`. Use `prisma migrate diff --script` to get raw SQL, hand-edit in the backfill `UPDATE`, apply via `prisma migrate deploy`. `server/prisma/migrations/20261005105346_federation_identity_model/migration.sql` is a worked example (backfilled `homeserverDomain` for pre-existing local users). A migration cannot see `SERVER_DOMAIN`, so that backfill and the communities one wrote the literal `'localhost'`, which made every such user fail `findLocalUserByUsername` (login 401). Anything a migration can only guess at has to be repaired at startup instead: see `server/src/lib/localDomainRepair.ts`, run from `index.ts` after the migrations, idempotent, and careful about the `(username, homeserverDomain)` unique key.

## Repo-specific conventions

- **Every federatable object has a `protocolId` (ULID), separate from its local DB id.** API responses only ever expose `protocolId`, never the DB id. Follow this for any new federatable model.
- A remote user is an ordinary `User` row with `isRemote: true`, carrying the **real** `protocolId` from their home server — never generate a fresh one for a remote stub. Getting this wrong broke cross-server presence/message matching once; see the protocolId regression test in `server/test/integration/federation.test.ts`.
- `publicUser(user, viewerId?)` hides `INVISIBLE` presence as `OFFLINE` unless `viewerId === user.id`. Pass `viewerId` at any new "render another user" call site — omitting it safely defaults to hiding, which is deliberate, not a bug to paper over.
- Any new WebSocket event tied to a specific conversation/channel must carry that id in its payload (`conversationId`/`channelId`). Relying on implicit context caused real message cross-contamination between an open DM and an open channel once.
- Key a `useEffect` off `user?.id`, not the whole `user` object from `AuthContext` — `user` gets a new object identity on every profile/presence refresh, not just login/logout. Getting this wrong in `WsContext.tsx` caused presence changes to silently revert; see its regression test.
- Windows dev note: in this shell, `cd X && long-running-cmd &` only applies the `cd` inside the backgrounded job, not the parent shell, because `&&` binds tighter than `&`. Wrap it: `(cd X && long-running-cmd &)`.
- Postgres is mapped to host port **5433**, not 5432 (see `docker-compose.yml`) — many dev machines already have something on 5432. Redis (optional, see below) is on **6380**, not 6379, same reasoning.
- All WebSocket delivery goes through `sendToUser`/`sendToUsers` in `server/src/ws/gateway.ts` — never write to the module's `connections` map directly from elsewhere, and never call a socket's `.send()` outside that file. With `REDIS_URL` set, those two functions publish to Redis instead of delivering directly (see `server/src/ws/presenceFanout.ts`); calling anything lower-level would bypass cross-replica fan-out silently.
- Prisma on Alpine (`server/Dockerfile`) needs **two** separate fixes, not just one: `binaryTargets` in `schema.prisma` (controls `@prisma/client`'s query engine) *and* `apk add openssl` in the image (the `prisma` CLI's own migration engine does its own OpenSSL auto-detection by shelling out to `openssl`, which Alpine doesn't ship by default). Missing either one fails silently at the wrong layer - a `prisma generate` that looks fine, then `prisma migrate deploy` crashing at container start with an opaque "Could not parse schema engine response" error that doesn't mention OpenSSL at all. Since the image is published for both amd64 and arm64, `binaryTargets` needs **both** musl variants (`linux-musl-openssl-3.0.x` and `linux-musl-arm64-openssl-3.0.x`) - missing the arm64 one wouldn't fail the build, only the arm64 container at startup.
- `server/src/startupChecks.ts` runs two checks in `index.ts`'s `main()` before the server listens: it refuses to start a deployment (`NODE_ENV=production`, which the Docker image sets, or a packaged binary) whose JWT secrets are unset/placeholders or whose `SERVER_DOMAIN` is unset (a warning under `npm run dev`; `ALLOW_INSECURE_DEFAULTS=true` overrides), and it refuses to start against a database whose `_prisma_migrations` has migrations this version doesn't ship (`ALLOW_UNKNOWN_MIGRATIONS=true` overrides). The first judges `configuredEnv`, a snapshot `config.ts` takes at the moment it reads the environment, **not** `process.env` at check time: `required()` applies its fallback silently, and Prisma loads `server/.env` into `process.env` when `@prisma/client` is imported - after `config.ts` has already settled on its fallbacks - so a later read can describe different values than the ones the server is actually using (found when a test run with `DOTENV_CONFIG_PATH` pointing nowhere reported "placeholder" secrets instead of "not set"). The migrations check looks in `prisma/migrations` relative to the working directory (`/app` in Docker, `server/` in dev) or `installDir` for a packaged binary, and skips with a warning if it can't find it.
- `TRUST_PROXY` (`server/src/lib/trustProxy.ts` -> `app.set("trust proxy")` in `app.ts`; `server.trustProxy` in the chart, `TRUST_PROXY` in `docker-compose.selfhost.yml`) is what makes `req.ip` - the rate limiter's key - the real client behind a reverse proxy or ingress. Left unset, every user behind the proxy shares ONE rate-limit bucket (10 auth attempts per 15 minutes for everyone): reproduced behind Traefik on kind, a second client got 429 while the same client going straight to the server got 401. It is deliberately strict: a hop count or a list of loopback/linklocal/uniquelocal/IPs/CIDRs, and `true` or a catch-all range is refused at startup, because trusting an `X-Forwarded-For` a client can set lets it pick its own rate-limit identity. Don't loosen that to be convenient. The chart's NOTES warn when an ingress is enabled without it.
- `server/docker-entrypoint.sh` runs `node dist/checkDatabaseExists.js` (`server/src/checkDatabaseExists.ts`) BEFORE `prisma migrate deploy`, because the migrate CLI **creates** a database that does not exist and carries on - a typo in the database name at the end of `DATABASE_URL` used to become a new, empty database with a new federation identity, and the server started happily. The native binaries never had this (their Prisma client fails with P1003); the check makes the container match. It only reacts to P1003: an unreachable server or bad credentials (checked first by Postgres) are left to `migrate deploy` and the server to report in their own words. `CREATE_DATABASE_IF_MISSING=true` skips it. The server also logs `Connected to database "x" on host:port: N local account(s)` at startup (never the credentials: `lib/databaseTarget.ts`). `scripts/start.ps1` runs `prisma migrate deploy` directly and is not covered, but its database comes from `docker-compose.yml`'s `POSTGRES_DB`.
- All nine permission bits are enforced (`server/src/lib/permissions.ts`), and `client/src/lib/permissions.test.ts` fails if the server defines a bit the role editor doesn't offer - so a new bit can't be added without deciding what it does. `DELETE_MESSAGES` (delete others' messages in a community channel; DMs stay sender-only) and `REACT` (add a reaction; removing your own never needs it) are checked in `messages/routes.ts` and in the federation home-side handlers; `MANAGE_EMOTICONS` (edit/delete a *local* community's emoticons, not a cached remote community's) in `emoticons/routes.ts`. Always take the permissions from the **message's own** community (`messages/communityAuth.ts`), never from a community id in a URL, and have the federated handlers check the message really belongs to the community and channel the URL names: both used to be trusted, which would have let a moderator of one community act on another's messages by mixing ids, and let any member react to any message. Creating a community emoticon is still open to every member (not gated by `MANAGE_EMOTICONS`).
- Both Dockerfiles build from the **repo root** as context, not their own directory (npm workspaces - the root `package-lock.json` is needed). `docker build -f server/Dockerfile .`, not `cd server && docker build .`.
- `client/Dockerfile`'s `deps`/`build` stages are pinned to `FROM --platform=$BUILDPLATFORM ...`, deliberately *not* following the target platform in a multi-arch (amd64/arm64) build. The build output (static JS/CSS/HTML) is platform-independent, and `vite build`'s native esbuild/rollup binaries are known to hang indefinitely under GitHub Actions' QEMU user-mode emulation - a real incident, not a hypothetical: the arm64 leg hung for over an hour in CI before this fix, despite building fine in under a minute locally (different QEMU implementation). Only the final nginx `runtime` stage actually varies per target arch. `server/Dockerfile` could not use the same trick (its `npm ci` runs Prisma's postinstall, which must run a binary for the target arch), and it did hit the emulation problem: `npm ci` on the arm64 leg intermittently died with `qemu: uncaught target signal 4 (Illegal instruction)` and BuildKit then hung instead of failing (#153). So `.github/workflows/publish-images.yml` no longer emulates anything: each image is built per architecture on a native runner (`ubuntu-latest` / `ubuntu-24.04-arm`), pushed by digest, and joined into one multi-arch tag by a `merge` job (`docker buildx imagetools create`); every job has a `timeout-minutes` so a stuck build fails instead of sitting there. Don't re-add `setup-qemu-action` to it. A manual run with the `push` input unticked builds everything without publishing.
- `server/src/wellknown.ts` is mounted in `app.ts` **before** the app-wide `cors(corsOptions(config.corsOrigins))` middleware, with its own permissive `cors()` scoped to the `/.well-known` path (mounted without a path it answered *every* OPTIONS preflight on the server with `*` before the app policy was consulted). This is deliberate, not an oversight to tighten later: a browser-based home-server picker needs to read this document from a domain the user just typed in, which by definition isn't in any configured origin allowlist. Every other route stays behind the configured `CORS_ORIGIN` list (comma-separated bare origins, parsed and validated by `lib/corsOrigins.ts`; an origin not in it gets no `Access-Control-Allow-Origin` at all).
- `FEDERATION_ENABLED=false` makes a server private (#109 phase 1; `docs/deployment/private-server.md`). It is parsed by `lib/federationEnabled.ts` and **strictly**: only true/false/1/0/yes/no/on/off, anything else refuses startup, because a typo must never leave a private server public - never loosen it to "anything but false". Guards sit at a few chokepoints, not at every call site: inbound `/federation/v1/*` is refused `403 federation_disabled` by `middleware/federationEnabled.ts` BEFORE the signature, nonce or peer lookup; outbound, `resolvePeer` (which `federationFetch` always calls) throws `FederationDisabledError`, and the outbox guards enqueue, flush and the worker. Mutation testing showed more guards than that were redundant, so don't add one "to be safe" without showing a test that fails without it. `FederationDisabledError` becomes 403 in the error middleware, so a route that lets it through needs no code. Remote events are QUEUED while private (still PENDING, attempts 0), not blocked, and delivered when it is switched back on; new remote relationships (friend request, DM/group, join, remote-community invites/messages via the proxy) are refused. The other direction matters just as much: a PEER's `403 federation_disabled` (`isPeerFederationDisabled`) is "not now", so the outbox retries it (`peer_federation_disabled`) and `proxyToHomeServer` reports 502 `federation_unreachable`; treating it as a rejection would mark queued events FAILED and lose them for good. Presence pushes are skipped. The client learns it only from the discovery document (`lib/federation.ts`, `useFederationEnabled`: ONE shared in-flight fetch, since several components ask at once) and hides or disables remote affordances, with `PrivateServerNotice` on remote conversations and communities; `isRemoteIdentity` decides what counts as remote. Changing it needs a restart.
- `FEDERATION_ALLOWED_DOMAINS` / `FEDERATION_BLOCKED_DOMAINS` (#109 phase 2) limit WHICH servers it talks to; the policy is `config.federationPolicy` (`lib/federationPolicy.ts`, `isPermitted(domain)`, read at the moment of each decision so tests swap it). Parsed strictly like the switch (exact domains with an optional port, no wildcards; a malformed entry or a domain in both lists refuses startup; an EMPTY list means no limit, so "talk to nobody" is `FEDERATION_ENABLED=false`, never an empty allow list). It reuses the phase 1 chokepoints and adds no new ones: `middleware/federationDomain.ts` after the on/off middleware (judges the CLAIMED `X-Federation-Origin`, BEFORE the signature, so a blocked or unlisted domain is never fetched and a forged origin cannot make the server look anything up; the same `403 federation_domain_blocked` for blocked and not-allow-listed), `resolvePeer` (`FederationDomainBlockedError`, mapped to 403 by the error middleware), `resolveOrFetchUser`'s explicit check (without it a lookup failure could read as "no such user"), and the outbox enqueue/flush/worker (events for a domain not permitted stay PENDING with 0 attempts, other domains are not held up) plus the presence push. A PEER's `403 federation_domain_blocked` is "not now" exactly like `federation_disabled`: `peerRefusal(res)` returns which one, the outbox retries it (`peer_federation_domain_blocked`) and the proxy reports 502 `federation_unreachable`; treating it as a rejection would FAIL queued events. The discovery document is unchanged and never lists who is allowed. The client does NOT know the lists (it learns only from a refusal): `federationRefusalMessage(code)` in `lib/federation.ts` is the one place that maps `federation_disabled` / `federation_domain_blocked` to words, so a new site that handles federation errors uses it instead of comparing codes. The Helm `chat.validate` refuses a domain in both lists at install time, and CI renders the chart for both (note `! grep` does not fail a step under `bash -e`; use `if grep ...; then exit 1; fi`).
- A person can hide from other servers (#109 phase 3): `User.discoverable` (default true; a migration adds it, so nobody changes silently), narrowed by `FEDERATION_USER_DISCOVERABILITY` (`default-on` | `default-off` | `forced-off`, `lib/userDiscoverability.ts`, strict parse; `effectiveDiscoverable` lets the server only narrow). Hidden means a server with no relationship is told the person does not exist: `isVisibleToDomain` (`modules/users/discoverability.ts`) is the ONE decision, used by the three federation handlers that reveal a local person (`GET /users/:username`, inbound `POST /friend-requests`, and a local member of an inbound `POST /conversations`), and each answers exactly as for a missing person (same status, same body). Two things are easy to break: (1) the check must run when the person does NOT exist too (`const visible = await isVisibleToDomain(user, ...)` BEFORE `if (!user || !visible)`; do not write `!user ||` first), so a missing and a hidden person cost the same and cannot be told apart by timing (a test counts the relationship queries); (2) a relationship (`hasRelationshipWithDomain`: friendship, PENDING request either way, shared conversation, shared or hosted community) keeps a server able to find them, which is what makes hiding not break existing friends, DMs and communities; domains compare case-insensitively. It is a setting about being FOUND: it is not a block and does not stop people on the same server (`GET /users/search`, local friend requests and profiles are untouched). `discoverable` is shown to its owner only (`publicUser`'s self-only fields), `discoverabilityLocked` only by `GET`/`PATCH /users/me` (`selfUser`), and `PATCH` with `discoverable` under `forced-off` is 409 `discoverability_locked`. The client shows it in Settings -> Privacy (`PrivacySection`), and says nothing on a server that predates it (no field). Who may SEND a request or DM beyond being findable is not done (the next phase).
- Who may START something with a person (#109 phase 3b): `User.contactPolicy` (`ANYONE` default | `SHARED_COMMUNITY` | `LOCAL_ONLY`; a migration adds it, so nothing changes silently; the server can set the default for new accounts and a LIMIT, see the defaults bullet below). The rule is pure and in one place, `contactAllowed` (`lib/contactPolicy.ts`: a FRIEND is always allowed; then the policy), and the facts come from `contactFacts`/`canContact`/`canContactIdentity` (`modules/users/contact.ts`). It applies to STARTING things only, never to an existing conversation or friendship: local `POST /friends/requests` judges after the already-friends / already-pending answers, and local `POST /conversations` judges AFTER an existing DM has been found (an existing DM stays openable). The recipient's server is the authority and answers EARLY as well as late: `GET /federation/v1/users/:username?from=name` adds `contact: { allowed }` (the sender passes `contactBy.username` through `resolveWithContact`, so a refusal is 403 `contact_not_allowed` before anything is sent), and the inbound handlers decide again (a refused friend request is NOT stored and gets an ordinary decline callback so the sender sees it as declined; a refused conversation is 403 and not created; an already-delivered request or existing conversation is left alone). A group is judged against the creator (`createdBy` in the `/conversations` payload, optional for older peers, in which case every other member must be allowed) and is all-or-nothing. `sharesCommunity` is only computed for people who chose SHARED_COMMUNITY (it can cost questions to other servers): the local tables answer for communities this server hosts, but a community hosted ELSEWHERE is cached with only our own members and the owner, so `sharesRemoteCommunity` asks each such host (`GET /federation/v1/communities/:id/membership`, answered only to a server that already has a member there; at most 10 hosts, 3 s each, anything but a clear yes is no). Don't "fix" that by trusting the sender's claim or by guessing from the cached member list. The client words every refusal the same whichever choice was made (`lib/contact.ts`), and `PrivacySection` selects a radio at once and reverts if saving fails (a controlled radio that waits for the server looks like a dead click).
- The directory (#109 phase 5) is `DIRECTORY_ENABLED` (strict boolean, OFF by default, `lib/directorySetting.ts`; `features.directory` in the discovery document) over three things that each opt in separately: a community is listed only when its managers choose `PUBLIC` (`Community.visibility`, joinable exactly like UNLISTED), a person only when they tick `User.listedInDirectory` (default false) AND are findable (`discoverable` and not `forced-off`: hiding wins, in `listListedPeople`), and nothing at all unless the operator turned the directory on. The listing code is `modules/directory/service.ts` (newest first by `protocolId`, a ULID, with the last one on the page as the cursor; hosted-here communities only, never cached remote ones; pictures made absolute with `toAbsoluteMediaUrl`; a search goes through `literally()` because Prisma's `contains` does NOT escape `%` and `_`). A server answers its own people at `GET /api/v1/directory/{communities,people}` and other servers at `GET /federation/v1/directory/...` (404 `directory_disabled` when it publishes none, so "none" is told from "unreachable"). Browsing ANOTHER server is `?domain=` on the local route: this server asks it with a signed federation call (`proxyToHomeServer`), never the person's browser, so private mode, the allow/block lists and the SSRF guard all apply for free and the person's address is not shown to that server; the answer is a stranger's text, so `sanitizeCommunityPage`/`sanitizePeoplePage` (`lib/directory.ts`) check every item and drop what is wrong, force `domain` to the server that was asked, accept only absolute http(s) pictures and cap a page at 50 - don't pass a peer's page through raw. The client's `BrowsePage` shows everything as text, drops the answer to an older question (`asked` ref, for failures too), joins by `<id>:<domain>` (the ordinary join) and adds friends by `username:domain`. In the e2e stack `alice.test` publishes a directory and `bob.test` does not (`e2e/scripts/run-server.mjs`), and the directory is shared by every test running at once, so e2e tests search for their own unique username or community name.
- Server defaults and limits (#189) follow one rule: a DEFAULT is only what a NEW account or community starts with (`FEDERATION_CONTACT_POLICY_DEFAULT`, `COMMUNITY_VISIBILITY_DEFAULT`, `DIRECTORY_PEOPLE=default-on`; existing ones are never touched), and a LIMIT can only NARROW what someone chose, never widen it, and lifting it brings their choice back, so the CHOICE IS ALWAYS STORED AS MADE and the limit is applied where it is READ. Contact: `contactAllowedUnderLimit(person, limit, facts)` is `both allow` (friends always in; the two policies are not ordered, so it is an intersection, not a min), used by `canContact`/`canContactIdentity`, and `needsSharedCommunity(person, limit)` decides whether to pay for the shared-community question. Communities: `effectiveVisibility(stored, config.communityVisibilityLimit)` (order least to most exposed to other servers: LOCAL_ONLY < INVITE_ONLY < UNLISTED < PUBLIC) is what EVERY reader uses instead of `community.visibility` - joining, the cards, the federation 404/403s, the snapshot sent to other servers, the serialized community, and the directory (nothing listed unless the limit is PUBLIC) - so a new reader of `.visibility` must go through it; the PATCH refuses a wider choice (409 `visibility_limited`) and also clamps the legacy `openJoin` mapping. `COMMUNITY_VISIBILITY_DEFAULT` unset follows the limit, and an explicit default wider than the limit REFUSES startup (`checkVisibilityDefault`). People in the directory: `DIRECTORY_PEOPLE` (`lib/directoryPeople.ts`, same three modes as findability; `forced-off` -> `listListedPeople` is empty and `PATCH listedInDirectory` is 409 `directory_listing_locked`). The signed-in person is told what applies (`contactPolicyLimit`, `directoryPeopleLocked` in `selfUser`; a community carries `visibilityLimit`) so Settings can disable what cannot take effect and say why. There is no e2e for the limits: the e2e servers are shared by every test at once, so a limit would change all of them; the integration tests (`serverDefaults.test.ts`) cover them.
- The end-to-end suite (`e2e/`, #56) is a workspace of its own with no `version` (so release-please has nothing to bump). Its servers start on `chat_e2e_a`/`chat_e2e_b` and `e2e/scripts/run-server.mjs` runs `prisma migrate reset` on them, so it refuses any database not named `*_e2e_a`/`*_e2e_b` - never loosen that, and never point `E2E_DATABASE_URL_BASE` at a server you care about. Every test makes its own users through the real sign-up form (`signUp`), so tests are independent and parallel; don't share accounts or rely on the order tests run in. Prefer roles/labels/placeholders to CSS classes, and wait by asserting, not sleeping (a sleep is only for proving something does NOT happen). A control that shows the choice at once and saves afterwards (the Privacy and "Who can join" radios) passes `toBeChecked()` before it is saved, so a test that then reloads cancels the save: wait for the PATCH response (`page.waitForResponse`) first. A race that usually goes one way is forced the other with `page.route` (see the "echo before the reply" test) - and as with any regression test, revert the fix and watch it fail. - Tauri v2's Windows WebView2 serves the app from the origin `http://tauri.localhost`, not `http://localhost:<port>` or a `tauri://` scheme - confirmed empirically (the server's `CORS_ORIGIN` has to match this exactly for real API calls to succeed through the desktop app, discovery itself works regardless since `.well-known` has its own permissive CORS). Hasn't been verified on macOS/Linux, where Tauri uses the OS's own WebKit instead of WebView2 and the effective origin may differ - confirm this for real before assuming it's the same everywhere.

On a dev machine with `VITE_API_URL` set in `client/.env` (the normal single-server local dev setup), the desktop app in dev mode will show fixed-server-mode UI, not the picker - this is correct/expected, not a bug, and doesn't reflect what a real packaged build does. `npm run tauri -- build` runs `vite build` the same way `npm run build` does, so it's subject to the exact same `.env`-presence behavior the home-server-picker tests already have to account for - verify picker mode in a real build by temporarily removing `client/.env` first, matching how CI's clean checkout (no `.env` file at all) actually builds it.

It's skipped specifically when the domain resolves via `FEDERATION_PEER_OVERRIDES` (operator-set local dev config, e.g. the `alice.test`/`bob.test` demo pointing at real `localhost` ports) - that's operator-trusted, not attacker input, and must keep working unguarded.
- Two `express-rate-limit` instances must never share the same `RedisStore` key prefix, even when one is meant to "stack" more strictly on top of the other (`server/src/middleware/rateLimit.ts`'s `generalLimiter` + `authLimiter`, both keying on the same `req.ip` for `/api/v1/auth/*` requests) - express-rate-limit's own `ERR_ERL_DOUBLE_COUNT` validation throws if it ever sees the same `(store, prefixed key)` pair incremented twice for one request, which is exactly what two differently-scoped limiters sharing a prefix would do. Give each limiter its own `RedisStore({ prefix })`.
- Rate-limit thresholds (`RATE_LIMIT_MAX` / `AUTH_RATE_LIMIT_MAX`, see docs/security.md "Rate limiting") are read from env with low production defaults (300 / 10 per 15 min) - `test/setupEnv.ts` raises both way up by default so ordinary integration-test traffic (e.g. a single file registering a dozen users) never trips them incidentally; `test/integration/rateLimit.test.ts` and `rateLimit.redis.test.ts` are the two files that intentionally override them back down to actually exercise the 429 behavior, restoring the env vars in their own `afterAll` the same way `presenceFanout.test.ts` restores `REDIS_URL`.
- `docker-compose.selfhost.yml` has its own top-level `name:` (`federated-chat-app-selfhost`) specifically so it doesn't share a default Compose project name (and therefore volumes/network) with the plain `docker-compose.yml` dev file when both sit in the same directory - without it, Compose derives the project name from the directory alone, not the `-f` filename, and the two files' same-named services (`postgres`) would collide. Required vars (`SERVER_DOMAIN`, `POSTGRES_PASSWORD`, both JWT secrets, `CLIENT_PUBLIC_URL`, `SERVER_PUBLIC_URL`) use Compose's `${VAR:?message}` interpolation so `docker compose up` fails fast with a clear message instead of silently starting the server with its dev-insecure JWT fallback (`server/src/config.ts`'s `required(name, fallback)`) - confirmed empirically that an unset required var does abort `docker compose config`/`up` before any container starts. The client's `API_URL` is fetched by the browser, not proxied through nginx (see `client/nginx.conf` - no `/api` location block), so `CLIENT_PUBLIC_URL`/`SERVER_PUBLIC_URL` must be real externally-reachable addresses, never the Compose-internal `server`/`client` service hostnames.
- `charts/federated-chat-app/templates/server-deployment.yaml` needs an `initContainer` that blocks on Postgres's TCP port before the main container starts - confirmed for real on a local kind cluster that without it, the server's entrypoint (`prisma migrate deploy`) races the Postgres pod at startup and crashes with `P1001: Can't reach database server`, causing a CrashLoopBackOff that only self-resolves once Postgres happens to win the race. Kubernetes `Deployment`s have no native equivalent of `docker-compose.selfhost.yml`'s `depends_on: condition: service_healthy` - this is the standard workaround. Only needed when `postgresql.enabled` (the bundled Postgres); not applicable to `externalDatabase.url`.
- The chart's required values (`domain`, `server.publicUrl`, `server.clientPublicUrl`, both JWT secrets, `postgresql.auth.password` when bundled) are enforced via a shared `chat.validate` named template (`_helpers.tpl`) that calls Helm's `fail` function, included at the top of every template that needs them - not Helm's own `required` function inline, since several of these need an *either/or* check (e.g. `secrets.jwtAccessSecret` OR `secrets.existingSecret`) that `required` alone can't express. Mirrors `docker-compose.selfhost.yml`'s `${VAR:?message}` fail-fast philosophy. The same template refuses `server.replicaCount > 1` with `disk` uploads that are not `ReadWriteMany` (a ReadWriteOnce claim left the second replica stuck in `Init` with a Multi-Attach error while `helm` reported success; `server.uploads.allowUnsharedWithReplicas` is the opt-out), and CI's helm job checks each case.
- `charts/federated-chat-app/Chart.yaml` has two version fields kept in lockstep via `release-please-config.json`'s `extra-files` (type `"yaml"` with `jsonpath`, confirmed supported by release-please's actual docs, not just inferred from the existing `"toml"` entry): `version` (the chart's own packaging version) and `appVersion` (the app version it deploys, and `values.yaml`'s default image tag via `{{ default .Chart.AppVersion .tag }}`) - both get bumped on every release, same as `tauri.conf.json`/`Cargo.toml`.
- Stored media URLs (`User.avatarUrl`, `Attachment.url`, `Emoticon.imageUrl`) can be *either* relative (`/uploads/x.png`, under the disk storage driver) *or* absolute (always under the S3 driver - see `server/src/lib/storage/`) - any code that forwards one elsewhere (to a browser, to a federation peer) must go through `toAbsoluteMediaUrl()` (`server/src/lib/mediaUrl.ts`), never string-concatenate `config.baseUrl`/`homeserverBaseUrl` onto it directly. Found and fixed a real bug this way: `conversations/routes.ts`'s outbound federation attachment relay did exactly that naive concatenation, which would have silently produced a broken, double-prefixed URL the moment any attachment's URL was already absolute (true for every upload once S3 storage shipped, not just a theoretical edge case).
- `server/src/lib/storage/diskStorage.ts` and `s3Storage.ts` take their settings via constructor options, not by importing `config.js` directly - `server/src/lib/storage/index.ts` is the one place that reads `config.*` and wires it into whichever adapter's constructor. Needed because `config.ts` has module-level side effects (`required("DATABASE_URL")` with no fallback) that throw in the plain unit-test environment (`vitest.config.ts`, no `DATABASE_URL` set - unlike the integration suite's `test/setupEnv.ts`) - confirmed by temporarily hiding `server/.env` and running `npm run test`. Any new `src/lib/**` module meant to have real unit tests should take this same shape rather than importing `config.js` at module scope.
- `PATCH /api/v1/users/me`'s `avatarUrl` used to require `z.string().url()`, which rejects the relative `/uploads/x.png` URL `POST /api/v1/media/upload` actually returns under the disk storage driver (the normal case) - setting an avatar through the Settings UI was broken end-to-end, with zero test coverage to have caught it. Fixed to `z.string().min(1)`, matching `Attachment`/`Emoticon` schemas elsewhere that already got this right. Found while building S3 storage support, which needed the same relative-vs-absolute URL question answered precisely anyway.
- Don't add `s3rver` (or similar) as a dependency for testing S3 code against a real local server - its own dependency tree has unresolved high-severity vulnerabilities (a `dicer`/`busboy` parsing crash, `fast-xml-parser` prototype pollution) with no non-breaking fix, which fails `npm audit --audit-level=high` (CI's `dependency-audit` job checks dev dependencies too, not just production ones). `@aws-sdk/client-s3`'s own S3 storage driver tests mock `S3Client` instead (see `server/src/lib/storage/s3Storage.test.ts`) - real wire-protocol-level S3 verification wasn't done for this project (Docker Hub blocked pulling `minio/minio` in the sandbox this was built in: "pull access denied... may require docker login").
- `server/src/lib/federation/client.ts` and `outbox.ts` would form a circular import if `client.ts` imported `outbox.ts` directly to call `flushOutboxForDomain()` on a successful delivery - `outbox.ts` already has to import `client.ts` for `federationFetch` itself. Solved with dependency inversion instead: `client.ts` exposes `setOnDeliverySuccess(fn)` and calls whatever's registered (a no-op if nothing is) after a successful response; `outbox.ts` registers `flushOutboxForDomain` as a module-load side effect. `client.ts` has zero knowledge `outbox.ts` exists. A retry driven by the outbox itself passes `skipOutboxFlush: true` so it doesn't re-trigger its own flush pass (harmless either way - the per-row claim makes a re-triggered flush just find nothing left to do - but pure waste otherwise).
- `flushOutboxForDomain()` (called right after a fresh successful `federationFetch` to that domain) must query by `status` alone, ignoring `nextAttemptAt` entirely - using the same "is it due" query the background worker uses (which *does* check `nextAttemptAt`) defeats the entire point of flushing promptly on fresh evidence a peer is reachable again, since a row backed off 55 minutes earlier just wouldn't be due yet. Got this wrong on the first pass; caught by an integration test asserting `nextAttemptAt` was still well in the future immediately before calling `flushOutboxForDomain` and expecting delivery anyway.
- Presence pushes (`presence/presenceStore.ts`) are deliberately NOT routed through the federation outbox, unlike friend requests/conversation handshakes/message relays - presence is current-state-only; retrying a stale push after a peer comes back would deliver outdated status (and there's no ordering story for "which of several queued presence updates is actually current" the way there is for messages, where `createdAt` already gives a natural order).
- A new Prisma migration doesn't apply itself to the `chat_test` integration-test database the way `npm run dev`/`scripts/start.ps1` apply it to the dev one - `DATABASE_URL="postgresql://chat:chat@localhost:5433/chat_test" npx prisma migrate deploy` (from `server/`) needs to be run by hand once after creating a migration, or `test:integration` fails with `P2021: The table ... does not exist`, not an obviously-migration-shaped error. See docs/testing.md. Also remember to add any new table to `test/helpers/db.ts`'s `resetDb()` `TABLES` list, or rows from one test leak into the next - and put it **before** any table it references without `ON DELETE CASCADE`: `resetDb()` empties them with `DELETE` in that order (one transaction), not `TRUNCATE`, because `TRUNCATE ... CASCADE` of the 24 tables cost ~300 ms before each of ~290 tests and `DELETE` costs ~6 ms. It also resets the one auto-increment counter (`SyncEvent.seq`) by hand, which `TRUNCATE ... RESTART IDENTITY` used to do. `enqueueFederationEvent` records the event and RETURNS: the first delivery attempt runs in the background (`DeliveryScheduler`, `lib/federation/deliveryScheduler.ts`), never inside the request, because a dead peer used to hold the sender's response for the whole retry cycle per domain. Attempts to one domain run in queued order (a message and its edit must arrive in order), different domains run concurrently, a domain that just failed is skipped for 5 s (the worker's backoff covers it), outbox attempts time out after `FEDERATION_OUTBOX_TIMEOUT_MS` (10 s), and the worker (`processDueOutboxEvents`) only starts on a domain once its OLDEST unfinished event is due - not any due row, or events skipped by the cooldown (their own timer is already past) would be delivered ahead of the older one that is still backing off - and both it and `flushOutboxForDomain` stop a domain's pass at the first row that must be retried so nothing is sent past an older event. So a test that checks what a peer received must `await waitForPendingDeliveries()` after the request (exported from `outbox.ts`), and `resetDb()` does the same before it deletes rows. `FEDERATION_RETRY_BASE_MS` (500 in `src/config.ts`, 1 in `test/setupEnv.ts`) is the pause between the 3 in-request attempts of one outbound federation call: nearly every federation test delivers to a fake unreachable peer such as `alice.test`, and at 500 ms that was a flat 1.5 s of sleeping per delivery (it made single tests take 3-5 s); the outbox's own, much longer backoff is separate and untouched. `BCRYPT_ROUNDS` defaults to 12 in `src/config.ts` and is set to 4 only in `test/setupEnv.ts` (`passwordHashing.test.ts` pins both); a server started as a deployment refuses a value under 10.
- Signing a bodyless GET for a federation request (or a test constructing one by hand) must hash an empty string, not `"{}"` - `client.ts`'s `federationFetch` does `method === "GET" ? "" : JSON.stringify(options.body ?? {})` specifically because of this; a GET carries no body, and `req.rawBody` is `undefined` server-side (falls back to `""` in `federationAuth.ts`), not `"{}"`. Signing against `"{}"` for a GET produces a signature that will never verify. Cost an hour chasing a false "nonce cache is broken" failure that was actually just this.
- `server/src/lib/federation/nonceCacheAdapters.ts` (the `InMemoryNonceCache`/`RedisNonceCache` classes) is split out from `nonceCache.ts` (the config-driven selector) for the same reason `diskStorage.ts`/`s3Storage.ts` are split from `storage/index.ts` and `outboxBackoff.ts` is split from `outbox.ts`: anything that imports `config.js` (even transitively, via `redis.js`) throws on missing `DATABASE_URL` in the plain unit-test environment. This is now an established pattern in `server/src/lib/**` - a module meant to have real unit tests takes its settings via constructor/function arguments and never imports `config.js`/`redis.js`/`db.js` itself; only the thin selector at the top of the dependency chain does, and that one is covered by integration tests instead.
- `test/helpers/factory.ts`'s `registerUser()` returns a serialized `PublicUser` - its `user.id` is the **protocolId**, not the local DB id a Prisma relation (`ConversationMember.userId`, etc.) actually references. A test that seeds a `ConversationMember`/similar fixture directly (bypassing the API) needs its own `prisma.user.findUniqueOrThrow({ where: { protocolId: registered.user.id } })` first - using `registered.user.id` directly fails with an opaque `Foreign key constraint violated` error, not an obviously identity-shaped one.
- Federation's message-edit/delete vs. reaction endpoints deliberately use two different ownership-proof shapes, both mirroring an existing precedent rather than inventing a third: edit/delete (`POST /messages/{id}/edit|delete`) carry no actor identity in the body at all - ownership is purely the message's already-cached `sender.homeserverDomain` matching `X-Federation-Origin`, the same shape `POST /friend-requests/{id}/accept|decline` already used for "only the thing's own owner can resolve it." Reactions (`.../reactions[/remove]`) carry an explicit `fromProtocolId`/`fromUsername`/`fromDomain`, the same shape `POST /messages` uses for a sender - because the reactor genuinely isn't already known information the way a message's own sender is, and might need `ensureRemoteUser`-caching for the first time.
- `messages/routes.ts`'s local edit/delete/react/unreact handlers and `federation/routes.ts`'s received versions share `localMessageRecipients`/`getRemoteConversationDomains` (`server/src/modules/messages/federationRelay.ts`) and `messageInclude` (`server/src/modules/messages/serialize.ts`) - extracted specifically so the federation-received handlers emit the *exact* same WS sync events (`message:edited`, `message:deleted`, `message:reaction_added/removed`) the local ones already did. This is why the client needed zero changes for federated edit/delete/reactions to work: `ConversationPage.tsx` already handled these events generically, with no awareness of (or need to know) whether the change originated locally or over federation.
- `server/src/modules/auth/totp.ts`'s `confirmTotpSetup()` deliberately does **not** persist the confirmation code's time-step into `User.totpLastUsedStep` - only `verifyTotpLogin()` does. TOTP is deterministic per 30-second step, so the code a user types to confirm setup can be numerically identical to the code they'd type on their very next login attempt if both happen within the same window (a completely normal, fast "enable then immediately log back in" flow). Persisting the step at confirm time would make that first real login fail as a false "replay," through no fault of the user - caught by an integration test asserting login still works immediately after setup.
- `signTotpChallengeToken()`/`verifyTotpChallengeToken()` (`server/src/lib/auth.ts`) sign the 2FA login-challenge token with a secret *derived* from `config.jwtAccessSecret` via HMAC (a fixed label, no new env var), not the secret itself - `requireAuth`'s `verifyAccessToken()` call uses `jwtAccessSecret` directly, so a challenge token's signature simply can't verify there. This is what stops a 2FA challenge token (handed back by `POST /auth/login` before the second factor is checked) from ever being usable as a real access token, even though both are ordinary JWTs signed by the same server.
- `federation/routes.ts`'s receiving `POST /conversations` handler trusts a member differently depending on who's vouching for them (own domain: must already exist locally; the calling peer's own domain: trusted directly from the payload; any other domain: independently verified via that domain's own `GET /users/{username}`, never trusted secondhand) - this closes a real cache-poisoning risk: `ensureRemoteUser()`'s upsert never overwrites `protocolId` on conflict (only `displayName`/`avatarUrl`/`homeserverBaseUrl`), so a calling peer that could claim an arbitrary `protocolId` for a *third-party* domain would plant it permanently, breaking that real user's identity matching forever once they actually federate for real. See `protocol/federation.md`'s "POST /conversations" section.
- `getServerKeyPair()` (`server/src/lib/federation/keys.ts`) had a genuine first-boot race: two concurrent callers before `ServerIdentity` exists could both pass the `findUnique` check and both attempt `upsert`'s `create`, and the loser threw a raw `P2002` unique-constraint error instead of falling back to the winner's row - the existing "upsert so whoever wins, everyone agrees" comment was wrong about `upsert` alone being race-safe. Never triggered before because nothing used to make two genuinely concurrent federation calls from one request; group-DM federation's parallel third-party-member verification (above) does exactly that, and surfaced it as a real, reproducible test failure (not flaky - two `Promise.all`-concurrent `resolveOrFetchUser()` calls against a freshly-reset DB hit it deterministically). Fixed with an in-process in-flight-promise dedupe (closes the same-process race) plus a `P2002` catch-and-reread fallback (closes the genuine cross-replica race the comment was trying to describe).
- Stored presence is cleared at startup by `startPresenceMaintenance()` (`ws/presenceMaintenance.ts`, logic in `lib/presenceReset.ts`), and it must never be a blanket "set everyone offline" when other replicas are running: that marked users connected to the *other* replicas offline, for good (#160, reproduced with two containers). With Redis it uses the `ws:conn:*` keys (one per live socket, any replica) as the truth for who is connected and a `ws:replica:*` key per running replica to tell "alone" (reset everything, as a single server always did) from "others are serving" (reset only users with no live connection), plus a sweep every minute for crash leftovers. `SIGTERM` is a graceful drain (`index.ts`, `lib/shutdown.ts`, `closeGatewayConnections()`): WebSockets are closed with 1001 so clients reconnect elsewhere, every step is time-bounded, and the chart's `preStopDelaySeconds` keeps the ingress from routing to a pod that is stopping. A test that needs the Redis-backed behaviour sets `REDIS_URL` itself and must import `config`-reaching helpers dynamically afterwards (see `presenceReplicas.test.ts`), since static imports are hoisted above the assignment.
- Route modules use plain `express.Router()` - and must keep doing so. Express 4 ignores what a handler returns, so a rejected promise from an `async` handler is an unhandled rejection that terminates the whole process (one bad request takes the server down for everyone); `server/src/lib/asyncErrors.ts` fixes that once, globally, by patching the route-registering methods on `express.Router` so a rejection reaches `next(err)`, installed by `lib/installAsyncErrors.ts`, which `app.ts` imports **first** (ES imports run in order, so a plain call inside `app.ts` would come after the route modules had registered their handlers). The last middleware in `app.ts` answers `{ error: "internal_error" }` (500, logged with the request line via a constant format string, detail never sent to the client) or, for client errors such as malformed JSON, a 4xx in the same `{ error }` shape. Do **not** replace this with a wrapper function around `Router()` that route modules import instead: that was tried first (#93) and CodeQL's `js/missing-rate-limiting` then reported 66 high alerts on `master`, because it only recognises routers created by `express.Router()` and so could no longer connect `app.ts`'s rate limiter to the handlers behind it - and PR checks only surface alerts on changed lines, so it was invisible until the PR merged. Regression tests: `test/integration/asyncErrors.test.ts` and `src/lib/asyncErrors.test.ts`.
- A log call must not put a value from outside in its FORMAT string: `console.error("[federation] delivery to %s failed:", domain, err)`, never `` console.error(`... ${domain} ...`, err) ``. CodeQL reports the second as `js/tainted-format-string` (high, so it blocks the CodeQL check), and which values count as "from outside" changes as code changes: alert #100 appeared on a log line that had been there for months, once a change began passing the origin a peer claims into the outbox. `src/logFormatGuard.test.ts` fails on a template-literal log call interpolating `domain`/`origin`/`username`/`identity`/`input`/`peer` (the server's own `config.*` is fine).

## Testing philosophy

There was no automated testing before this project's CI/test suite was added —
every early bug was found by manual browser testing. A meaningful chunk of the
integration suite is regression tests written directly against real bugs found
that way (presence leaking true status over REST, message cross-contamination,
federation protocolId mismatches, the WsContext reconnect bug) — each has a
comment explaining the original bug and why the test catches it. When fixing a
bug, add a test in that style, not just a prose explanation in the PR.

## Git workflow

**`master` is protected** — direct pushes are rejected by the repo ruleset
("Require PR"), and it applies to everyone including the owner (empty bypass
list). All work goes through a branch and a pull request.

- **Branch names**: `<type>/<short-description>`, matching the commit types
  below — e.g. `feat/federated-group-dms`, `fix/presence-invisible-leak`,
  `chore/bump-prisma`.
- **Commit messages**: [Conventional Commits](https://www.conventionalcommits.org/) —
  `<type>[optional scope]: <description>`. Examples:
  - `feat(federation): relay typing indicators across servers`
  - `fix(client): stop WsContext reconnecting on presence refresh`
  - `test(server): add regression test for message cross-contamination`
  - `docs: document the federation demo restart-resilience check`
  - `chore: bump vitest to 5.1`

  Common types: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `chore`,
  `ci`, `build`. Add a scope (`server`, `client`, `federation`, or a module
  name) when a change is obviously scoped to one area; omit it for
  repo-wide changes. This applies to **every commit**, not just the final one
  on a branch.
- **Merging**: squash-only (the only merge method the ruleset allows). The PR
  title becomes the squash commit's message — **write the PR title as a
  Conventional Commit too**, since that's what ends up in `master`'s history.
- Required approvals are set to 0 (solo maintainer — GitHub won't let you
  approve your own PR), so **passing required status checks is the actual
  merge gate**, not review.
- **Never hand-edit `CHANGELOG.md`** — [release-please](https://github.com/googleapis/release-please)
  (`.github/workflows/release-please.yml`) generates it from Conventional Commit
  PR titles automatically, and a manual edit just gets overwritten. This makes
  the PR title double as the changelog entry, so write it the way a reader of
  `CHANGELOG.md` would want to see it, not a terse commit-log summary. Version
  numbers are lockstep across `package.json`/`server/package.json`/
  `client/package.json` — see `docs/versioning.md` for the full bump policy (pre-1.0,
  breaking changes bump MINOR, not MAJOR) and exactly how a release gets cut
  (short version: release-please opens a standing Release PR as commits land;
  merging it is the one manual step, and it's what controls release timing).

## What the `master` ruleset currently enforces

("Require PR" ruleset, Settings → Rules → Rulesets)

- Require a pull request before merging — 0 required approvals, squash-only merge method
- Require status checks to pass — all 8 CI jobs pinned as required: `Lint`,
  `Typecheck & build`, `Unit tests`, `Integration tests`,
  `Dependency vulnerability audit`, `Dependency review (PR diff)`,
  `Secret scanning`, `CodeQL analysis`. Also requires branches to be up to date
  before merging.
- Require code scanning results — **CodeQL**, blocking on Security alerts "High or higher" / Alerts "Errors"
- Require linear history
- Restrict deletions, block force pushes
- Bypass list: empty

**Not enabled**, deliberately:
- Required approvals beyond 0 — would make the repo unmergeable solo
- "Require code quality results" — no tool produces that specific result type yet
- "Restrict code coverage" — GitHub's native version needs a specific coverage-upload mechanism this repo doesn't produce; the real coverage gate is the `integration-tests` CI job's own enforced threshold instead (see docs/testing.md "Coverage")

`.github/workflows/ci.yml` (the jobs, for a pull request that changes code):
`lint`, `typecheck-and-build`, `unit-tests`, `integration-tests` (enforces the
coverage floor), `dependency-audit`, `dependency-review` (PRs only),
`secret-scan`, `codeql`. A first job, `changes`, picks a tier with
`.github/scripts/ci-tier.mjs` and the others skip themselves when it is not `full`:
a docs-only PR runs only the secret scan and CodeQL, a release-please PR whose diff is
provably only version numbers skips the two test suites, and a push to `master` runs only
CodeQL (see docs/testing.md "What runs when"). Skip with job-level `if:`, never a `paths:`
filter on the workflow (that leaves the required checks pending and blocks the merge), never
skip CodeQL on a PR, and treat a failed `changes` job as "run everything".
